# 4. Servo pacing 设计

使用 `StrictPacer`：

```text
- never catch up
- never burst backlog
- late > 2 * period 时 realign
- 不补发积压帧
- late_policy = REALIGN_AND_CONTINUE_NEVER_CATCH_UP
```

重要认识：

```text
late_frames
```

只统计正 lateness，本身不是最重要指标。

真正关注：

```text
pulse latency
mean / median / p99 / max
realigns
```

观察到长期规律：

```text
max_late ≈ pulse_max - period
```

说明大延迟发生在同步的：

```python
sdk.armPluseToServo(ARM_ID, vec)
```

调用链内部，而不是 q 计算或 Python 插值。

# 8. Stationary Pulse Probe

文件：

```text
probe_pulse_latency_stationary.py
```

核心设计：

```text
- 读取当前位置
- 构造一个固定 FloatVector
- 每 20 ms 重复发送同一个 q
- 不做轨迹变化
- 只测 armPluseToServo() latency
```

关键配置：

```python
ROBOT_IP = "192.168.8.148"
LOCAL_IP = "192.168.8.244"
ARM_IP   = "192.168.8.148"
ARM_PORT = 8080
ARM_ID   = 1
N        = 300
PERIOD_S = 0.020
```

调用：

```python
code = sdk.armPluseToServo(ARM_ID, vec)
```

这一步非常重要，因为它证明：

> 即使 q 完全不变，`armPluseToServo()` 仍然会随机出现几十、几百甚至几千毫秒长尾。

因此轨迹生成、插值、VAJ、路径本身不是主要原因。

# 9. strace 排查

## 9.1 完整 syscall trace

使用：

```bash
strace -f -ttt -T -yy \
  -e trace=sendto,recvfrom,sendmsg,recvmsg,send,recv,\
poll,ppoll,select,pselect6,epoll_wait,futex,\
nanosleep,clock_nanosleep \
  -o pulse_corr_strace.log \
  python3 -u probe_pulse_latency_stationary.py
```

发现：

```text
主线程在慢 armPluseToServo() 期间
主要等待在 native SDK 的 epoll/futex
```

并不是在 Python 计算 q。

但完整 futex/epoll strace 对 timing 影响很大，因此绝对时间不能直接作为真实 latency。

---

## 9.2 Network-only strace

```bash
strace -f -ttt -T -yy \
  -e trace=network \
  -o pulse_network_strace.log \
  python3 -u probe_pulse_latency_stationary.py
```

观察：

```text
runtime sendmsg/recvmsg syscall 自身一般是微秒级；
真正的大时间空档出现在 syscall 之间。
```

结论：

> Linux 本地 send/recv syscall 执行不是主要瓶颈。


这是 STA+AP / repeater 并发结构。
