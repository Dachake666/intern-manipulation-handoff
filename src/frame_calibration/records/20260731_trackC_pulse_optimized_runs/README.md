## 结论：这次优化是倒车

**现场评价：丝滑程度不如未优化的 v1。** 日志【高度支持】以下判断——
注意日志没有逐帧关联记录，无法证明每个迟到帧都恰好落在采样帧上：

- 总时长全是 **12.50s，偏差 +0.00s** —— 不是整体变慢，是**局部尖峰**；
- 跟随误差采样是**每 10 帧一次 = 5Hz**，迟到帧中位数 10 帧，与 62 个采样帧
  数量级相当 —— 代码结构、5Hz 周期、现场观感三者一致指向采样；
- 根因：`follow.maybe_sample()` 内部 `read_follow_error` 是**两次** SDK 往返
  （`fb=False` + `fb=True`），塞进 20ms 预算的热循环里。

**铁律：任何阻塞式 SDK 读取都不该进透传热循环。**

## 附带发现：手册比装的 SDK 轮子新

4 个按手册写的接口在真机上不存在或签名不同：

```
armGetPosReFreshMS   本机没有这个属性
armUnsetLoad         本机没有这个属性
armGetAxisParameter  第三参要枚举 AxisParameterIndex，不是 int
armSetRobotLoad      本机签名是 (int, int)，不是 (int, LoadParameter)
```

所以「限位核对 / 刷新周期 / 负载告知」三项**全部没生效**（有 try/except 兜住，
没让运行崩掉）。**净效果：零收益 + 一个 5Hz 微顿。**

后续新接口一律先跑 `probe_sdk.py` 探明再用。

## 跟随误差数字要打问号

六次运行平均都是 0.82~0.86°，几乎不变。0.85° ÷ 10°/s = 85ms 滞后。这个值稳定得
可疑——`fb=True` 的反馈刷新周期是 40ms（`armSetPosReFreshMS` 没生效），读到的
可能是最多 40ms 前的旧值，相当部分可能是**测量伪影**而非真实滞后。
改成用「我们刚发出去的点」比对后，这个歧义消掉。
